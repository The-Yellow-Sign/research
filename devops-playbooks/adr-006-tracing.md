# Выбор системы распределенной трассировки: Jaeger vs Datadog

## Контекст
С переходом на микросервисную архитектуру (Go/Python) отладка цепочек вызовов стала крайне сложной. Нам необходимо решение для Distributed Tracing, которое позволит визуализировать жизненный цикл запроса от API-шлюза до базы данных.

## Рассматриваемые варианты

### 1. Jaeger (Open Source)
- **Плюсы**: Бесплатно, полный контроль над данными, поддержка OpenTelemetry.
- **Минусы**: Требует поддержки собственной инфраструктуры (Elasticsearch/Cassandra для хранения).

### 2. Datadog APM (SaaS)
- **Плюсы**: "Из коробки", отличная интеграция с логами и метриками, отсутствие проблем с поддержкой БД.
- **Минусы**: Высокая стоимость (оплата за каждый хост/сервис), данные хранятся на сторонних серверах.

## Сравнение функционала

| Характеристика | Jaeger | Datadog |
| :--- | :--- | :--- |
| **Сложность внедрения** | Средняя | Низкая |
| **Стоимость** | Низкая (только ресурсы) | Высокая |
| **Визуализация** | Базовая | Продвинутая |
| **Интеграция с K8s** | Нативная (Operator) | Нативная (Agent) |

## Решение
Принято решение использовать **Jaeger** на этапе разработки и тестирования, так как наши требования к безопасности запрещают передачу полных трасс во внешние SaaS-решения на данном этапе.

### Архитектура внедрения
- Сбор данных через OpenTelemetry Collector.
- Хранение в существующем кластере [Elasticsearch](es-tuning.md).
- Визуализация через Jaeger Query UI.

## Последствия
- Необходимо выделить дополнительные ресурсы в K8s для `jaeger-collector` и `jaeger-query`.
- Потребуется обучение разработчиков работе с инструментами OpenTelemetry.

> ⚠️ IMPORTANT: Убедитесь, что Sampling Rate настроен на 1-5%, чтобы не перегрузить сетевой канал и хранилище.

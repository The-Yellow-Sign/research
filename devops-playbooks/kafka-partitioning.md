# Стратегия партиционирования топиков в Kafka для High-Load сервисов

## Контекст
С ростом объема данных в нашем основном кластере Kafka (более 1 млн сообщений в секунду), стандартное количество партиций (3) перестало обеспечивать необходимую пропускную способность.

## Решение
Мы переходим на динамическую схему расчета количества партиций на основе ожидаемой нагрузки и количества консьюмеров.

### Сравнение подходов

| Параметр | Static (Current) | Dynamic (Proposed) |
| :--- | :--- | :--- |
| **Кол-во партиций** | 3-6 | 32-64 |
| **Consumer Groups** | Ограничено | Масштабируемо |
| **Ребалансировка** | Редкая | Частая (при росте) |
| **Нагрузка на Broker** | Низкая | Средняя |

## Детали реализации
Для каждого нового топика необходимо следовать правилу: `N_partitions = Max(N_consumers, Throttle_MBs / 50)`.

- **Ключи партиционирования**:
    - Использовать `user_id` для сохранения порядка сообщений одного пользователя.
    - Использовать `null` ключ только для логов без необходимости порядка.
- **Репликация**:
    - Минимальный `replication.factor`: 3.
    - `min.insync.replicas`: 2.

### Алгоритм выбора ключа (Pseudo-code)
1. Проверить наличие `business_id`.
2. Если есть -> `hash(business_id) % partition_count`.
3. Если нет -> `round_robin()`.

> ⚠️ IMPORTANT: Увеличение количества партиций — это дорога в один конец. Уменьшить их количество без пересоздания топика невозможно.

## Последствия
- Плюсы: Устранение "узких мест" при чтении.
- Минусы: Увеличение потребления файловых дескрипторов на брокерах.

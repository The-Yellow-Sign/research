# Выбор Redis в качестве основного кеширующего слоя для микросервисов на Go

## Контекст
В связи с ростом нагрузки на основную базу данных PostgreSQL, возникла необходимость внедрения распределенного кеша. Основные требования: низкая задержка (latency < 1ms), поддержка сложных структур данных и возможность горизонтального масштабирования.

## Рассматриваемые варианты
1. **Memcached**: Быстро, но поддерживает только строки. Нет персистентности.
2. **Redis**: Богатый набор структур данных, встроенная поддержка Lua-скриптов, возможность работы в режиме Cluster.
3. **Hazelcast**: Слишком тяжеловесно для текущего стека на Go.

## Почему Redis?
- **Производительность**: Redis обеспечивает суб-миллисекундный отклик при правильной настройке.
- **Библиотеки для Go**: Отличная поддержка библиотекой `go-redis`, которая реализует все необходимые паттерны (circuit breaker, pooling).
- **Pub/Sub**: Нам потребуется механизм инвалидации кеша между экземплярами сервисов, и Redis Pub/Sub идеально подходит для этой задачи.

### Сравнение задержек (Latency Comparison)

| Операция | Memcached | Redis (Single Node) | Redis (Cluster) |
| :--- | :--- | :--- | :--- |
| GET (1KB) | 0.2ms | 0.25ms | 0.4ms |
| SET (1KB) | 0.2ms | 0.3ms | 0.5ms |

## Архитектурная схема
Сервисы подключаются к Redis Sentinel для обеспечения высокой доступности. В будущем возможен переход на Redis Cluster при достижении лимитов по памяти на одной ноде.

```go
// Пример инициализации клиента в Go
import "github.com/go-redis/redis/v8"

var rdb *redis.Client

func initRedis() {
    rdb = redis.NewClient(&redis.Options{
        Addr:     "localhost:6379",
        Password: "", // no password set
        DB:       0,  // use default DB
    })
}
```

## Последствия
- Положительные: Снижение нагрузки на PostgreSQL на 40-60%.
- Отрицательные: Необходимость мониторинга еще одного критического компонента (Eviction rate, Memory usage).

# SRE Engineering Handbook: Глобальные стандарты платформы

Этот документ является основополагающим справочником для всех инженеров SRE и DevSecOps в нашей компании. Он объединяет в себе накопленный опыт, технические стандарты и культурные принципы, которыми мы руководствуемся при построении и эксплуатации систем.

---

## 1. Культура SRE

### 1.1. Error Budgets и SLO
Мы не стремимся к 100% доступности. Наша цель — доступность, достаточная для пользователя.
- **SLI (Service Level Indicator)**: Конкретная метрика (например, Latency 95-й перцентиль).
- **SLO (Service Level Objective)**: Целевое значение SLI (например, < 200ms для 99% запросов).
- **Error Budget**: 1 - SLO. Если бюджет исчерпан, все изменения (feature code) замораживаются, и команда фокусируется только на надежности.

### 1.2. Blameless Post-mortems
Сбои неизбежны. Мы не ищем виновных, мы ищем системные недостатки. Каждый критический инцидент заканчивается публикацией отчета в нашей базе.

## 2. Стандарты наблюдаемости (Observability)

Система считается наблюдаемой только если она реализует "Три столпа":

### 2.1. Метрики (Prometheus)
Все сервисы должны отдавать `/metrics` в формате Prometheus.
- **RED Pattern**: Rate (запросы/сек), Errors (ошибки/сек), Duration (длительность).
- **USE Pattern**: Utilization (загрузка), Saturation (насыщение), Errors (ошибки).

### 2.2. Логирование (Loki/ELK)
- Формат: Только JSON.
- Обязательные поля: `app_name`, `env`, `trace_id`, `user_id`, `severity`.
- [Руководство по Loki](loki-investigation.md)

### 2.3. Трассировка (Jaeger)
Каждый запрос через API Gateway должен получать `X-Trace-Id`, который пробрасывается через всю цепочку микросервисов.

## 3. Инфраструктура как код (IaC)

Мы не настраиваем сервера вручную. Любое изменение должно проходить через Git.

### 3.1. Terraform
- Модульность: Используйте общие модули из приватного реестра.
- State: Храните только в S3 с блокировкой через DynamoDB.
- [План миграции на IaC](bare-metal-to-k8s-migration.md)

### 3.2. Helm
- Никаких захардкоженных значений. Все конфигурируется через `values.yaml`.
- Используйте `helm-secrets` для работы с конфиденциальными данными.

---

## 4. Стандарты надежности (Reliability)

### 4.1. Автомасштабирование
- **HPA (Horizontal Pod Autoscaler)**: Обязательно для всех stateless сервисов.
- **VPA (Vertical Pod Autoscaler)**: Рекомендуется для подбора оптимальных лимитов в dev-среде.

### 4.2. Graceful Shutdown
Приложение должно корректно завершать работу.
- Обработка `SIGTERM`.
- Завершение текущих запросов перед выходом.
- Закрытие соединений с БД.

### 4.3. Circuit Breaker
Используйте библиотеки (например, Resilience4j или возможности Istio) для предотвращения каскадных сбоев. Если зависимый сервис "упал", ваш сервис должен вернуть дефолтный ответ или ошибку быстро, не удерживая поток.

## 5. Процесс On-Call (Дежурство)

Дежурный инженер — это первая линия обороны.

### Правила дежурства:
1. **Response Time**: Реакция на ACK алерта в PagerDuty — не более 15 минут для P0.
2. **Handover**: Передача смены происходит через краткий звонок или отчет в Slack.
3. **Primary/Secondary**: Всегда есть основной дежурный и "тень" для подстраховки.

### Ранбуки:
Для каждого критического алерта ДОЛЖЕН существовать ранбук.
- [Пример: Ошибки 502 в Nginx](03-nginx-502-bad-gateway.md)
- [Пример: Репликация Postgres](11-postgresql-replication-guide.md)

## 7. Безопасность (DevSecOps)

### 7.1. Секреты
- **Запрещено**: Хранение секретов в Git (даже зашифрованных через git-crypt).
- **Разрешено**: HashiCorp Vault, AWS Secrets Manager.
- [Инцидент с сертификатами Vault](vault-root-ca-expiration.md)

### 7.2. Сканирование образов
Образы автоматически сканируются в Nexus/Trivy перед деплоем. Образы с критическими уязвимостями блокируются.

## 10. Глоссарий

- **Toil (Рутина)**: Работа над эксплуатацией, которая является ручной, повторяющейся и автоматизируемой. Наша цель — < 50% времени на Toil.
- **Freeze**: Период запрета на внесение изменений (например, Черная Пятница).
- **Unseal**: Процесс открытия доступа к зашифрованным данным в Vault.

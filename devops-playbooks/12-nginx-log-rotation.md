# Ротация логов в Nginx

## Введение

Для продакшн‑окружения важно регулярно ротировать логи Nginx, чтобы избежать переполнения диска и упростить анализ. Правильная настройка logrotate обеспечивает сохранность исторических данных и минимальное влияние на производительность.

## Требования

- ОС: Linux (Ubuntu 20.04+, CentOS 8+)
- Nginx версии 1.18+ (доступ к конфигурационным файлам)
- Пакет `logrotate` установлен (обычно предустановлен в дистрибутивах)

## Пошаговая инструкция

### Шаг 1: Убедитесь, что logrotate установлен

```bash
sudo apt-get install -y logrotate   # Debian/Ubuntu
# или
sudo yum install -y logrotate       # RHEL/CentOS
```

### Шаг 2: Создайте конфигурацию для Nginx

```ini
# /etc/logrotate.d/nginx
/var/log/nginx/*.log {
    daily                     # ротировать ежедневно
    missingok                 # игнорировать отсутствие файлов
    rotate 30                 # хранить 30 архивов (≈ месяц)
    compress                  # сжимать старые файлы gzip'ом
    delaycompress             # не сжимать последний архив сразу
    notifempty                # не ротировать пустые файлы
    create 0640 www-data adm   # создаём новый файл с правами
    sharedscripts             # запускать скрипты один раз для всех файлов
    postrotate
        # Перезапускаем Nginx, чтобы он открыл новый лог‑файл
        if [ -f /run/nginx.pid ]; then
            kill -USR1 `cat /run/nginx.pid`
        fi
    endscript
}
```

**Пояснения к ключевым параметрам**
- `daily` – ежедневная ротация; можно заменить на `weekly`/`monthly` в зависимости от нагрузки.
- `rotate 30` – хранит 30 архивов, что покрывает ~30 дней.
- `compress` и `delaycompress` – экономят место, но последний архив остаётся в открытом виде для быстрого доступа.
- `postrotate` – посылает сигнал `USR1` Nginx, заставляя его переоткрыть файлы логов без полной перезагрузки.

### Шаг 3: Тестирование конфигурации

```bash
sudo logrotate -d /etc/logrotate.d/nginx   # dry‑run, проверка синтаксиса
sudo logrotate -f /etc/logrotate.d/nginx   # форсировать ротацию сейчас
```

Проверьте, что в `/var/log/nginx/` появился архивный файл `access.log.1.gz` (или `error.log.1.gz`).

## Проверка (Verification)

1. Убедитесь, что новые файлы логов созданы с правами `0640` и владельцем `www-data:adm`.
2. Проверьте, что процесс Nginx не перезапускается полностью (нет downtime) – запросы продолжают обслуживаться.
3. Просмотрите журнал `/var/lib/logrotate/status` – должна быть запись о последней ротации.
4. Сгенерируйте нагрузку и убедитесь, что новые записи идут в свежий лог‑файл, а старый архив остаётся неизменным.

# План аварийного восстановления (Disaster Recovery) для кластера Cassandra

Этот документ описывает критические шаги по восстановлению данных и работоспособности кластера Cassandra (версии 4.x) в случае полной потери одного региона или массового повреждения данных.

## 1. Введение и RTO/RPO

- **RTO (Recovery Time Objective)**: 4 часа (время до доступности кластера на чтение/запись).
- **RPO (Recovery Point Objective)**: 24 часа + время репликации WAL (максимально допустимая потеря данных).

## 2. Подготовительные данные

Перед началом восстановления убедитесь, что у вас есть доступ к:
1. Репозиторию бэкапов в S3 (хранилище снимков/snapshots).
2. Конфигурационному файлу `cassandra.yaml` для каждой ноды.
3. Топологии кластера (список нод, токенов и дата-центров).
4. Схеме данных (CQL-скрипты создания Keyspaces и Tables).

## 3. Сценарий A: Восстановление из Snapshot (основной регион жив)

Если данные были удалены или повреждены по ошибке приложения.

### Шаг 1: Остановка всех нод
```bash
nodetool drain
systemctl stop cassandra
```

### Шаг 2: Очистка текущих данных
Удалите commitlog и содержимое директорий данных.
```bash
rm -rf /var/lib/cassandra/data/*
rm -rf /var/lib/cassandra/commitlog/*
```

### Шаг 3: Восстановление из снимка
Для каждой ноды:
1. Скачайте нужный снимок из S3 в `/tmp/backup`.
2. Скопируйте файлы SSTable в директории таблиц.

```bash
# Пример для конкретной таблицы
cp /tmp/backup/my_keyspace/users-uuid/snapshots/backup-20250101/* /var/lib/cassandra/data/my_keyspace/users-uuid/
```

### Шаг 4: Импорт данных
Запустите Cassandra и выполните обновление индекса.
```bash
nodetool refresh -- my_keyspace users
```

## 4. Сценарий B: Восстановление в новом регионе (Full DR)

Если старый регион полностью недоступен.

### Шаг 1: Развертывание новой инфраструктуры
Используйте Terraform для создания нод в регионе Secondary.
```bash
cd terraform/cassandra-dr
terraform apply -var="region=eu-central-1"
```

### Шаг 2: Настройка конфигурации
Убедитесь, что `cluster_name` совпадает со старым, а `seeds` указывают на новые IP-адреса.
Крайне важно вручную прописать токены (`initial_token`), если вы хотите сохранить старое распределение данных без ребалансировки.

### Шаг 3: Восстановление данных через `sstableloader`
Это наиболее надежный способ при изменении топологии кластера.

```bash
# Запуск загрузчика
sstableloader -d <new_node_ip> /path/to/backup/my_keyspace/users/
```

## 5. Проверка целостности

После запуска всех нод выполните следующие проверки:

1. **Статус кластера**:
   ```bash
   nodetool status
   ```
   *Все ноды должны быть в статусе UN (Up Normal).*

2. **Запросы к данным**:
   Выборочно проверьте записи через `cqlsh`.
   ```sql
   SELECT count(*) FROM my_keyspace.critical_table;
   ```

3. **Запуск Repair**:
   Для синхронизации данных, которые могли быть пропущены:
   ```bash
   nodetool repair -full
   ```

## 6. Коммуникация при инциденте

1. **T+0**: Обнаружение сбоя, созыв On-call команды.
2. **T+15m**: Объявление статуса "Disaster" в канале #incidents.
3. **T+30m**: Принятие решения о способе восстановления (A или B).
4. **T+3h**: Завершение копирования данных.
5. **T+4h**: Открытие трафика для потребителей (Read-only вначале).

## 7. Важные замечания по безопасности

- Бэкапы в S3 должны быть зашифрованы ключом KMS.
- При восстановлении в новом облаке необходимо обновить правила Firewall (Security Groups) для доступа к межсервисному порту 7000/7001.

> [!CAUTION]
> Никогда не запускайте `nodetool repair` на всем кластере одновременно, это создаст критическую нагрузку на диск и сеть. Делайте это по очереди для каждой ноды.

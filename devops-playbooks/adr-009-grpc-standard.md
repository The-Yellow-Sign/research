# Архитектурное решение: Внедрение gRPC как стандарта для Service-to-Service коммуникации

## 1. Контекст и Проблема

На текущий момент большинство наших микросервисов общаются по HTTP/1.1 с использованием JSON (REST). С ростом количества сервисов и трафика мы столкнулись со следующими проблемами:

1. **Высокие задержки (Latency)**: Сериализация и десериализация больших JSON-объектов занимает до 30% времени обработки запроса.
2. **Отсутствие строгой типизации**: Ошибки в схемах данных обнаруживаются только в runtime, что приводит к сбоям на проде.
3. **Объем трафика**: Текстовый формат JSON избыточен по сравнению с бинарными протоколами.
4. **Endpoint Management**: Поддержка Swagger/OpenAPI спецификаций вручную часто приводит к рассинхрону документации и кода.

## 2. Предлагаемое решение: gRPC

Мы предлагаем использовать gRPC (Google Remote Procedure Call) на базе HTTP/2 и Protocol Buffers (protobuf) для всех синхронных вызовов между сервисами внутри контура.

### Почему gRPC?
- **Производительность**: Бинарный формат protobuf значительно компактнее и быстрее JSON.
- **HTTP/2**: Поддержка мультиплексирования (множество запросов в одном TCP-соединении) и Header Compression (HPACK).
- **Кодогенерация**: Клиенты и серверы генерируются автоматически из `.proto` файлов для всех наших языков (Go, Java, Python, Rust).
- **Streaming**: Нативная поддержка двунаправленных стримов (bi-directional streaming).

## 3. Сравнение Protobuf vs JSON

Ниже представлены результаты синтетических тестов для типичного объекта "Заказ" (Order):

| Параметр | JSON (REST) | Protobuf (gRPC) | Улучшение |
| :--- | :--- | :--- | :--- |
| **Размер сообщения** | 840 bytes | 180 bytes | ~4.6x |
| **Время сериализации** | 120 μs | 18 μs | ~6.7x |
| **Время десериализации** | 150 μs | 25 μs | ~6x |

## 4. План миграции

Миграция будет проходить в три этапа:

### Этап 1: Пилотный проект
Выбор двух высоконагруженных сервисов (например, `Billing` и `Inventory`) и реализация gRPC взаимодействия между ними параллельно с существующим REST.

### Этап 2: Общие библиотеки
Создание централизованного репозитория `proto-hub`, где будут храниться все `.proto` определения. Настройка CI для автоматической публикации клиентских библиотек (SDK) при изменении схем.

### Этап 3: Постепенный вывод REST
Все новые сервисы обязаны использовать gRPC. Старые сервисы переводятся на gRPC по мере планового рефакторинга.

## 5. Проблемы и риски

1. **Сложность отладки**: Бинарные данные нельзя просто прочитать через `curl`. Потребуются инструменты вроде `grpcurl` или `Postman` (с поддержкой gRPC).
2. **Балансировка нагрузки**: Стандартные L4 балансировщики плохо работают с HTTP/2 (соединения живут слишком долго). Требуется переход на L7 балансировку (Envoy, Istio или расширенный HAProxy).
3. **Браузерная поддержка**: gRPC нельзя напрямую вызвать из фронтенда (нужен gRPC-Web или прокси).

## 6. Примеры кода (.proto)

```protobuf
syntax = "proto3";

package orders;

option go_package = "github.com/company/proto/orders";

service OrderService {
  rpc CreateOrder (CreateOrderRequest) returns (OrderResponse) {}
  rpc GetOrderStream (UserRequest) returns (stream OrderResponse) {}
}

message CreateOrderRequest {
  uint64 user_id = 1;
  repeated Item items = 2;
}

message Item {
  string sku = 1;
  uint32 quantity = 2;
}

message OrderResponse {
  string order_id = 1;
  string status = 2;
  double total_price = 3;
}
```

## 7. Резюме и решение

Принято решение о переходе на gRPC. Это позволит сократить расходы на инфраструктуру за счет уменьшения CPU и Network трафика, а также повысить надежность за счет контрактного тестирования на уровне protobuf.
